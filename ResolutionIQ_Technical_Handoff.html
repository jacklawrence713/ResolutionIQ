5. Core Architecture — Eligibility Engine

The engine is the most critical part of the codebase. Understand this before touching anything.

5.1 Engine Functions

Five investor-specific functions, each returning the same shape:

evaluateFHA(loan: LoanData): EligibilityResult[]
evaluateFNMA(loan: LoanData): EligibilityResult[]
evaluateFHLMC(loan: LoanData): EligibilityResult[]
evaluateVA(loan: LoanData): EligibilityResult[]
evaluateUSDA(loan: LoanData): EligibilityResult[]

Return type:

interface EligibilityResult {
  option: string;        // e.g. "FHA 30-Year Standalone Modification"
  eligible: boolean;
  nodes: AuditNode[];    // every criterion evaluated
  note?: string;         // special conditions or warnings
}

5.2 The Node System

Every eligibility criterion is a "node" — a single pass/fail check. The node() helper is defined inside each engine function:

// Inside evaluateFHA:
const nodes: AuditNode[] = [];
const node = (question: string, answer: string, pass: boolean) => {
  nodes.push({ question, answer, pass });
};

// Usage:
node("Loan is FHA-insured", loan.loanType, loan.loanType === "FHA");
node("Delinquency >= 1 month", dlq + "mo", dlq >= 1);
// ...
const eligible = nodes.every(n => n.pass);
results.push({ option: "FHA Reinstatement", eligible, nodes });
Never compute eligible manually as a boolean expression. Always derive it from nodes.every(n => n.pass). This ensures the audit trail is always consistent with the eligibility outcome.

5.3 Terms Engine

calcApprovalTerms(optionName: string, loan: LoanData) — ~2,000+ lines. Computes:

  • New payment, new interest rate, capitalized UPB
  • Partial claim amounts, forbearance totals
  • Cap checks (LTV caps, UPB caps, payment increase caps)
  • Amortization schedule inputs for mods

This function is called when displaying results and in the Report tab. It is NOT called by the eligibility engine — they are separate concerns.

5.4 Waterfall Order

const WATERFALL_ORDER: Record<string, string[]> = {
  FHA: ["FHA Reinstatement", "Repayment Plan", "Formal Forbearance", ...],
  FNMA: ["FNMA Reinstatement", "FNMA Repayment Plan", ...],
  // etc.
};

Results are sorted by waterfall order before display. Options not in the waterfall array are appended at the end.

5.5 Servicer Overlays

Overlays are applied as a post-processing filter after the engine runs. If an option is eligible but the overlay excludes it, it is marked ineligible with a note. Currently stored in localStorage("riq_overlays").

7. Authentication & RLS

7.1 Auth Flow

  1. User registers → Supabase creates auth user → profiles row created with approved=false
  2. Admin sees pending user in Settings → User Management → clicks Approve → sets approved=true
  3. User logs in → loadProfile() reads profiles row → if not approved, shows "Pending" screen
  4. Profile includes role → UI gates features based on role

7.2 RLS Policies

Row Level Security is enforced at the Supabase database level:

  • specialist — can only read/write their own evaluations rows (user_id = auth.uid()) plus rows assigned to them (assignee_email = auth.email())
  • supervisor — can read all evaluations rows; can update assignee_email
  • admin — full access to all tables
If RLS-related permission errors appear, re-run the DB Setup SQL from Settings → Database Setup. It recreates all RLS policies idempotently.

9. Key Patterns & Conventions

9.1 negEscrow Pattern (all Payment Deferral options)

const negEscrow = escrowAdv > 0
  ? escrowAdv
  : (currentEscrow < 0 ? Math.abs(currentEscrow) : 0);

This is used in all 6 Payment Deferral options (FNMA, FHLMC, FHA, USDA, disaster variants). It resolves escrow advancement differently depending on whether the escrow advance balance or current escrow drives the deferred amount.

9.2 Loan Age Computation

const originationDate = loan.noteDate || loan.noteFirstPaymentDate;
const loanAgeMonths = originationDate
  ? Math.floor((Date.now() - new Date(originationDate).getTime()) / (30.44 * 86400000))
  : 0;

Not hardcoded. Used by FNMA, FHLMC, USDA engines for "loan must be ≥ X months seasoned" checks.

9.3 FIELD_MAP (LOS Import)

The FIELD_MAP constant maps every known LOS field name variant (camelCase, snake_case, human-readable) to the internal LoanData field name. When adding a new field to initLoan, add corresponding entries to FIELD_MAP.

9.4 HelpTip Component

<HelpTip text="Explanation of this field shown on hover" />

Inline tooltip icon. Use this for all investor-specific flags and any field that isn't self-evident from its label.

9.5 Num Component

<Num value={loan.upb} onChange={v => set("upb", v)} placeholder="e.g. 285000" />

Numeric input component used throughout. Handles string↔number coercion and formatting. Use this for all numeric fields — do not use raw <input type="number">.

12. Security Notes

  • The Supabase anon key in .env is a public publishable key — it is safe in client-side code. RLS policies enforce data access control at the database level.
  • The Supabase service role key is never used. Do not add it to the app.
  • The Claude API key for the AI assistant is entered by the user at runtime and never stored anywhere (not localStorage, not Supabase).
  • All evaluation logic runs client-side. No loan data is sent to any third-party service except Supabase (for saving cases).
  • The FRED PMMS fetch is a GET request to a public federal reserve endpoint — no loan data is included.
  • Loan data is PII-sensitive. Supabase RLS ensures users can only access their own cases (or their team's, for supervisors/admins). Verify RLS policies are active before any production deployment.

13. Definition of Done

  1. All 496 test cases pass (node [each test file].mjs)

  3. If a new field was added to initLoan: a corresponding entry was added to FIELD_MAP
  4. Build succeeds (npm run build completes with no errors)
  5. Feature tested manually in dev server at localhost:5173
  6. PR reviewed and approved before merge to master
